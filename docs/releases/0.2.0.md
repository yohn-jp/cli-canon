# CLI Canon 0.2.0

## Summary

0.2.0 is the first release in which CLI Canon is the normative authority for the standard CLI shell. It freezes and implements the Canon-first shell policy (#76), preserves the command/result discriminant at the Node execution boundary (#77), resolves Help intent with route-scoped grammar (#78), and makes the TypeScript type-certification program complete and observable (#79).

It is also the first published release of the canonical command tree, semantic runtime, composed command sources, and canonical help document work that landed on `main` after 0.1.7.

Normative authority is [`docs/architecture/CANON.md`](../architecture/CANON.md), in particular §6.2 (canonical help document), §11 (output rule and standard shell), and §17 (consumer migration). These notes summarize the consumer-visible consequences; they do not restate or override CANON.

## Canon-first shell policy

- CLI Canon owns the standard shell: root no-args, `--help`, `-h`, `--help=<mode>`, `--version`, the `--json` machine presentation selector, and the human and machine projections of framework failures (CANON §11.1).
- Products own command results, domain error decisions, authorization, lifecycle, and provider effects. They present results through `NodeCliResultPresenter` and map domain errors through `DomainErrorAdapter`.
- Migration is Canon-first (CANON §17). Each consumer migration carries its own change ledger that classifies every in-scope legacy behavior as `preserve-domain`, `converge-to-canon`, `transition-only`, or `special-surface` (CANON §17.1). A standard-shell behavior is `converge-to-canon` unless it satisfies §11.6; a legacy compatibility fixture is evidence for classification, not the target output.
- CLI Canon holds no product ledger, product compatibility table, or product-specific exception. Adding a command, adding an optional option, editing Help content, or extending a domain result remains a single-repository product change (CANON §17.2).

## Standard shell behavior

Shell resolution runs once per invocation, before route resolution (CANON §11.2):

- `--help`, `-h`, `--version`, and `--json` are reserved. A product field whose flag or alias uses one of them is rejected at construction with `FLAG_COLLISION`. 0.1.7 reserved only `--help` and `-h`; remove any product-local `--json` or `--version` field before upgrading.
- Tokens are scanned with the declared-option value rules used by Help detection. A token consumed as a declared option value is not a shell token, and no token after `--` is a shell token.
- Every scanned `--json` selects `machine` presentation; repetition is idempotent. `--json` is removed from the argv passed to the grammar backend and to delegated executors. `--json=<value>` is not the selector and fails as `unknown-option`.
- Root no-args (`<bin>`, or `<bin> --json`) is a `no-command` usage failure at the root target: stderr, exit `2`, never Help on stdout. A declared group route without a command segment is the same failure with the group's usage.
- Help wins over `--version` and over route resolution. Human mode writes the `summary` or `full` text to stdout with exit `0`. Machine mode writes the JSON discovery projection of the resolved target for every valid Help token. An invalid `--help=<mode>` is an `invalid-help-mode` usage failure.
- The only version request is argv `["--version"]` after `--json` removal. It prints `CompiledProduct.packageMetadata.version` followed by `\n`, or `{"name":…,"version":…}` in machine mode, on stdout with exit `0`. Supply `packageMetadata` from the product's own installed `package.json`; without it `--version` fails as `unknown-option`. Any other `--version` occurrence fails as `unknown-option`.
- Exit codes are fixed: `0` success, Help, and version; `2` usage and validation; `1` handler-result, unexpected, serialization, and budget. Presentation mode changes encoding only, never stream or exit code.

## Human and machine framework failures

Every framework failure is written to stderr (CANON §11.5).

- Human projections: `error: <usage message>\n\nUsage: <usage>\n`, `INVALID_INPUT: <message>\n`, `INVALID_HANDLER_RESULT: <message>\n`, and `UNEXPECTED: <message>\n` for unexpected failures and unmapped handler errors.
- Machine projections are one compact JSON document followed by `\n`:
  - `{"error":{"kind":"usage","code":…,"message":…,"usage":[…],"commandId":…,"option":…,"value":…}}`, with absent optional keys omitted;
  - `{"error":{"kind":"validation"|"handler-result"|"unexpected","message":…}}`.
- Backend diagnostics such as `parserCode` never appear in the machine document.
- A machine failure document over `maxOutputBytes` becomes the text `budget` failure; JSON is never truncated. `serialization` and `budget` failures keep the output-policy text diagnostic in both modes.
- Migration: a consumer that emitted its own JSON error envelope for standard framework failures under `--json` converges to these documents. Such an envelope is not a special surface (CANON §11.6).

## Domain result and error ownership

- The resolved `PresentationMode` (`"human" | "machine"`) is carried on every Node execution outcome as `presentation`. It is passed to `NodeCliResultPresenter`, to `DomainErrorAdapter.map(error, presentation)`, and to `DelegatedCommandRequest.presentation`. Products must not inspect argv or Canon-rendered output to recover it.
- Without a presenter, a successful result is its compact JSON on stdout in both modes. With a presenter, the product owns success presentation in both modes; in machine mode it must write one complete JSON document.
- A domain error matched by `DomainErrorAdapter` is rendered only by the product, with the product's output, stream, and exit code. Canon never wraps it. An unmatched handler error is a Canon `unexpected` failure. Framework failures never reach the adapter.
- `NodeCliSpecialTerminalSurface` is reserved for protocol, TTY-interactive, and long-running surfaces (CANON §11.6). Its callbacks are never applied in machine mode, and it is not a mechanism for restoring legacy Help, usage, or JSON error layouts.

## Node command/result discriminant

- `NodeCliSuccess<Catalog>` is now a union mapped over command IDs: each member pairs one `commandId` literal with that command's `result` type, plus `presentation`. A presenter that branches on `execution.commandId` narrows `execution.result` without casts, and a cross-command result access is a type error.
- `NodeCliSuccess` changed from an interface to a type alias. Code that extended or implemented it as an interface, or read command-specific result fields without narrowing on `commandId`, must narrow first.

## Public type changes

- Node execution outcomes gain a `status: "version"` member (`NodeCliVersion`) and a required `presentation` field on every member. Exhaustive handling of `NodeCliExecution` and hand-constructed executions passed to `projectNodeCliExecution` must account for both.
- `DomainErrorAdapter.map` receives `presentation` as a second parameter. Existing single-parameter implementations remain assignable.
- `CanonicalArgvOutcome` and `ComposedArgvOutcome` gain the version member and `presentation`. `CanonicalRuntimeProduct` gains optional `packageMetadata`.
- `CompiledProduct` defaults its `Groups` type parameter to `any`, and `CanonicalRuntimeProduct.tree` accepts any group catalog, so products compiled with declared groups are assignable where the group catalog is not specified.

## Route-scoped Help grammar

- Help intent is resolved with the option grammar of the root, group, or command scope being parsed, not a product-wide flag map. An unrelated command that declares the same after-route flag spelling with a different arity can no longer change another route's Help detection, and adding or reordering commands cannot change it.
- A required-value option consumes a following `--help` or `-h` as its value. Optional-value options, boolean flags, and `--opt=value` never consume a following Help token. Negative-number values are option values. Before the route, only `placement: "anywhere"` options consume a value. Tokens after `--` are payload.
- This changes behavior only for products that declared the same after-route flag spelling with different arity on different commands.

## TypeScript type certification

- `test/types/tsconfig.json` compiles every `test/types/*.ts` fixture together with `src/**/*.ts` under TypeScript 6.0.3. The previous configuration used a hand-maintained include list that omitted `composition-certification.ts`.
- Release-candidate certification records the actual `tsc --listFilesOnly` inclusion and proves that removing a negative multi-command discriminant assertion makes the type program fail.
- This is repository certification only; the published package surface is unchanged by it.

## Deprecated 0.1.x compatibility surfaces

These remain importable in 0.2.0 as `transition-only` migration aids (CANON §17.1). They are not extended and are not reported as conformant.

- `NodeCliTerminalAdapter` and the `terminalAdapter` option are deprecated. Only `terminalAdapter.success` is still applied, after `resultPresenter`, in both presentation modes. The `help` and `usageFailure` callbacks are ignored: standard Help and usage failures are always rendered by Canon. Move result presentation to `NodeCliResultPresenter` and only a genuine special surface to `NodeCliSpecialTerminalSurface`.
- The 0.1.7 help-presentation hook (`terminalAdapter.help`) therefore no longer changes Help output. The packaged README documents the 0.2.0 Canon boundary and no longer presents this hook as an active migration path.
- `legacyRoutes`, `LegacyRouteDescriptor`, `composeCommandProjection`, and `ComposedCommandProjection` are deprecated and still functional. Declare consumer-owned routes in a `DelegatedCommandSource`, pass it through `delegatedSources`, and use `composeCommandSources` with `projectComposedCommandTree` for direct projection.

## Compatibility

This is a breaking release for consumers that relied on product-owned shell controls, legacy Help/usage adapters, product-local `--json` or `--version` fields, or the widened `NodeCliSuccess` type. No consumer-specific compatibility shim is provided; consumers migrate through their own change ledger.
